# 質問項目・AGENTS.md出力仕様

## 結論

初期リリースでは、必須4問と任意1問の回答から、実用的な `AGENTS.md` をブラウザ内で決定的に生成する。

利用者へGit運用、テスト方針、AIエージェントの作業手順などを一つずつ質問しない。利用者はプロジェクト固有の事実だけを入力し、アプリが共通ベースラインと技術スタック別ルールを補って、実装・検証・Git／PR・安全上の制約・完了報告まで含む指示を組み立てる。

外部AI APIは使わない。補完する文言はこの仕様で定義した固定テンプレートから選ぶため、同じ回答から常に同じMarkdownを生成する。

この文書は、Issue #5の質問・回答データモデル、Issue #6の生成ロジック、Issue #7の質問UIが共有する仕様の一次情報とする。

## 解決したい課題

- 利用者が `AGENTS.md` に必要なルールを最初から設計しなくても、すぐ雛形を得られるようにする。
- 質問への回答そのものを負担にせず、プロジェクト固有の最低限の情報だけを求める。
- 少ない入力でも、AIエージェントが作業開始から完了報告まで迷いにくい内容を出力する。
- 入力されていないコマンド、外部サービス、権限など、事実として確認できない内容は捏造しない。

## 入力体験

- 初回表示では5問すべてを1つの短いフォームとして表示する。
- 必須は4問だけと明記する。任意質問は未回答でも警告や未完了表示を出さない。
- 詳細設定、ステップ式ウィザード、カテゴリごとの追加質問は設けない。
- 必須4問が埋まれば、その場で「AGENTS.mdを生成」を実行できる。
- コマンドは用途ラベルなしでも入力でき、1行1コマンドを貼り付けられる。
- 生成結果はプレビューで確認し、入力へ戻って再生成できる。

## 入力形式

| 入力形式 | 回答値 | UIと正規化のルール |
| --- | --- | --- |
| `text` | 文字列 | 単一行。前後の空白を除去し、途中の連続する空白と改行を半角スペース1つへまとめる。 |
| `textarea` | 文字列 | 複数行。改行をLFへ統一し、各行の先頭にあるタブと半角スペース、行末空白、先頭・末尾の空行を除去する。 |
| `list` | 文字列の配列 | 1行1項目。各項目を `text` と同様に正規化し、空項目を除く。入力順を維持する。 |
| `command-list` | `{ label?, command }` の配列 | コマンドを必須、用途ラベルを任意とする。ラベルは `text` と同じ単一行の正規化・エスケープを適用し、空コマンドを除いて入力順を維持する。 |

すべての自由入力は最大2,000文字、`list` は最大20項目、`command-list` は最大10項目とする。ただし、質問表で個別の上限を指定した場合は個別指定を優先する。

## 質問仕様

| 順序 | ID | ラベル | 説明・入力例 | 入力形式 | 必須条件 | 初期値 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `project.name` | プロジェクト名 | `AGENTS.md` の対象名。例: `在庫管理Web` | `text` | 必須、1〜100文字 | なし |
| 2 | `project.summary` | 何を作るプロジェクトですか？ | 対象ユーザー、解決する課題、提供するものを短く入力する。例: `小規模店舗の担当者が在庫を確認するWebアプリ` | `textarea` | 必須、1〜1,000文字 | なし |
| 3 | `technology.stack` | 技術スタック | 言語、フレームワーク、主要ライブラリを1行ずつ入力する。例: `TypeScript`、`React`、`Vite` | `list` | 必須、1〜20項目 | 空配列 |
| 4 | `commands.project` | プロジェクトで使うコマンド | install、dev、lint、test、buildなど、AIエージェントが使用してよいコマンドを1行ずつ入力する。用途ラベルは任意。 | `command-list` | 必須、1〜10項目 | 空配列 |
| 5 | `project.constraints` | 追加で守ってほしいこと | プロジェクト固有の禁止事項や注意だけを入力する。例: `本番データをテストに使わない` | `list` | 任意、0〜10項目 | 空配列 |

## アプリが補完する内容

入力負担を減らす代わりに、次の内容はアプリ側の固定テンプレートから補完する。

- 既存の指示、構成、命名へ合わせる実装方針
- 依頼範囲に限定した小さな差分
- 入力、空状態、エラー時にクラッシュさせない方針
- 関連する検証とテストの実行
- 作業前の確認、作業後の差分確認と報告
- 焦点を絞ったcommitとPRの方針
- 秘密情報、ユーザーの変更、技術スタックを保護する制約
- 技術スタックから安全に判定できる場合のコーディング規約

補完文言は利用者の回答を言い換えるAI生成ではない。以下の共通ベースラインと技術プロファイルから機械的に選択する。

## 共通ベースライン

すべての生成結果へ、次のルールを固定で含める。

### 実装方針

- リポジトリ内の指示、既存構成、命名、スタイルを優先する。
- 依頼された目的に必要な最小限の差分にし、無関係な変更や大規模リファクタリングを行わない。
- 新しい依存関係や外部サービスは、依頼で必要性が明確な場合だけ追加する。
- 入力不足、空状態、想定外の値、処理失敗でアプリ全体をクラッシュさせない。

### テスト・品質確認

- 変更箇所に関連する既存テストを実行し、振る舞いを追加または変更した場合は必要なテストを更新する。
- 回答で指定されたコマンドだけをプロジェクト固有コマンドとして扱い、存在を確認できないコマンドを捏造しない。
- 検証を実行できない場合や失敗が残る場合は、理由と未確認範囲を明確に報告する。

### Git・PR運用

- 変更は目的ごとに整理し、無関係なファイルをcommitへ含めない。
- commitやPRには、変更理由、主な変更、検証結果を簡潔に記録する。
- rebase、force push、履歴の書き換えは、明示的に依頼されない限り行わない。

### AIエージェントの作業手順

- 作業前に関連する指示、ドキュメント、既存実装、影響範囲を確認する。
- 仕様変更や依頼範囲の拡大が必要なら、実装前に利用者へ確認する。
- 作業後に差分を確認し、利用可能な関連検証を実行する。
- 完了報告には、実施概要、変更ファイル、検証結果、未対応事項または懸念点を含める。

### 禁止事項と安全上の制約

- 秘密情報、APIキー、個人情報をcommitまたは出力へ含めない。
- 利用者の未commit変更を削除、上書き、巻き戻ししない。
- 技術スタック、データ保存方式、外部API、認証、課金、解析を依頼なく変更または追加しない。
- 破壊的な操作は対象と影響を確認し、依頼範囲が明確な場合だけ実行する。

## 技術プロファイル

`technology.stack` の各項目へUnicode Normalization Form KC（NFKC）を適用し、小文字へ変換してから、英数字の単語境界または表に記載した複合語の完全一致で判定する。単純な部分一致は使わず、例えば `django` を `go` と判定しない。複数のプロファイルへ一致した場合は、表の上から順にすべて出力し、正規化後に完全一致するルールを重複排除する。

| プロファイル | 一致語 | 追加するルール |
| --- | --- | --- |
| TypeScript | `typescript` | `既存のstrict設定を維持し、型エラーを回避するためだけのanyや型アサーションを安易に追加しない。` |
| JavaScript | `javascript`, `node.js`, `nodejs` | `既存のモジュール形式と実行環境を維持し、暗黙の型変換へ依存しない。` |
| React | `react`, `next.js`, `nextjs` | `既存のコンポーネント構成と状態管理方針を維持し、UI変更では基本的なキーボード操作とアクセシビリティを確認する。` |
| Vue | `vue`, `nuxt` | `既存のComposition APIまたはOptions APIの選択と状態管理方針を維持する。` |
| Python | `python`, `django`, `flask`, `fastapi` | `既存のフォーマッター、リンター、型注釈の方針に合わせ、例外を握りつぶさない。` |
| Swift | `swift`, `swiftui`, `uikit` | `既存のデータフローと命名規則を維持し、UI状態の更新箇所を明確にする。` |
| Kotlin | `kotlin` | `既存のnull安全性、非同期処理、UIアーキテクチャの方針を維持する。` |
| Rust | `rust` | `所有権とエラー型を明確にし、回復可能な入力エラーへ安易にpanicやunwrapを使用しない。` |
| Go | `golang`, `go` | `gofmtに従い、エラーを明示的に処理し、既存のpackage境界を維持する。` |

どのプロファイルにも一致しない場合、技術固有ルールは追加せず、共通ベースラインだけを使用する。推測で近い技術を選ばない。

## 未回答・不正値の扱い

| 状態 | 必須質問 | 任意質問 | 出力 |
| --- | --- | --- | --- |
| 未回答 | 検証エラー。生成しない。 | 正常。 | 任意の追加ルールを省略する。 |
| 空白だけの文字列・空配列 | 未回答へ正規化し、検証エラー。 | 未回答へ正規化する。 | 出力しない。 |
| 壊れた値・型が異なる値 | 未回答へ正規化し、検証エラー。 | 未回答へ正規化する。 | 出力せず、アプリをクラッシュさせない。 |

初期リリースでは回答を永続保存しないが、Issue #5では外部入力や将来の保存値を安全に扱えるよう、この境界を型と正規化関数で表現する。

| 1 | タイトル・導入文 | `project.name` | 常に出力する。 |
| 2 | `## プロジェクトの目的` | `project.summary` | 常に出力する。 |
| 3 | `## 技術スタック` | `technology.stack` | 常に出力する。 |
| 4 | `## プロジェクトコマンド` | `commands.project` | 常に出力する。 |
| 5 | `## 実装方針とコーディング規約` | 共通ベースライン、技術プロファイル | 常に出力する。 |
| 6 | `## テスト・品質確認` | 共通ベースライン、`commands.project` | 常に出力する。 |

## 出力文言と変換規則

1. 見出し順は対応表の順で固定する。
2. 見出しの直後、段落の間、リストと次の見出しの間は空行を1行だけ入れる。
3. 箇条書きは `- ` を使用する。
4. 文末記号は利用者の回答を維持し、生成側で追加しない。
5. 末尾はLFを1つだけ付ける。CRLF、末尾空白、3行以上の連続改行は出力しない。
6. 同じ配列内で正規化後に完全一致する項目は、最初の1件だけを残す。
7. 技術プロファイルのルールは、入力された技術スタックの直後ではなく、実装方針の末尾へ追加する。
8. 追加の制約は、共通の禁止事項の末尾へ入力順で追加する。

### Markdownを壊さない処理

- `text`、`list`、`command-list` の用途ラベルは、バックスラッシュを先にエスケープした後、Markdownの制御文字 `` ` ~ = * _ { } [ ] ( ) < > # + - . ! | `` の直前へ `\` を付ける。
- `textarea` は行ごとに先頭のタブと半角スペースを除去してから同じエスケープを行い、元の改行を維持する。空行は最大1行まで維持する。
- URLを自動リンク化せず、入力文字列としてエスケープする。
- コマンドはインラインコードとして出力する。値に含まれる最長の連続バッククォートより1個長いバッククォート列を区切りとして使い、区切りの内側へ半角スペースを1つ置く。
- HTML、Markdown、テンプレート記法、シェル構文を実行・解釈しない。Markdownプレビューでも生HTMLを有効にしない。

### 例3: Markdown制御文字を含む入力

利用者の入力はMarkdownとして解釈せず、構造を壊さない形へエスケープする。

```markdown
# README\#生成API

このファイルは、このプロジェクトで作業するAIエージェント向けの指示です。

## プロジェクトの目的

\# 見出し風の入力から \[README\]\(未対応\) を生成するAPI

## 技術スタック

- Node\.js
```
